LEON Hub: Multi-Agent Orchestration Design

From single-agent CLI to federated multi-agent teams. A design document.

The Problem

LEON is currently a single-agent CLI tool. It works well for one human talking to one AI agent. But real work often needs multiple agents collaborating - a researcher, a coder, a reviewer.

What we want:

  • A web UI for managing teams of LEON agents
  • Agents that can interact with each other
  • Any local LEON instance should be able to become a server
  • Servers on different machines should connect to each other

The challenge: how do we add this without turning a lightweight CLI into a bloated platform?

Design Principles

  1. Local-first. Single machine works fully offline. Network is optional enhancement.
  2. Any node can serve. No privileged "master" - any LEON instance can become a server.
  3. Explicit messaging. Agents send messages explicitly, no magic sync.
  4. Fail loudly. Network issues visible, not hidden behind fallbacks.
  5. Progressive complexity. Simple case stays simple, complexity opt-in.

Architecture: Federated Model

Instead of a central server that manages all agents, we use a federated model. Each machine runs its own LEON server. Servers connect peer-to-peer.

Machine A Machine B +---------------------+ +---------------------+ | LEON Server | | LEON Server | | +-----+ +-----+ | HTTP/WS | +-----+ +-----+ | | |Agent| |Agent| |<--------->| |Agent| |Agent| | | | A1 | | A2 | | | | B1 | | B2 | | | +-----+ +-----+ | | +-----+ +-----+ | | | | | | | | +----+----+ | | +----+----+ | | | Local | | | | Local | | | | MsgBus | | | | MsgBus | | | +---------+ | | +---------+ | +---------------------+ +---------------------+

Key Properties

  • Each server manages its local agents
  • Servers connect peer-to-peer (no central registry)
  • Agent address: local_name or server_url/agent_name
  • Messages to remote agents routed through server connection

Message Queue Options

Agents need to send messages to each other. What's the right abstraction?

Approach Pros Cons
No queue (direct HTTP/WS) Simple, no deps Lost messages on failure
In-process queue (asyncio.Queue) Simple, no deps Single machine only
SQLite as queue Persistent, no extra deps Polling, not real-time
Redis Fast, pub/sub, proven Extra dependency

Decision: Start with SQLite-backed queue. We already have SQLite for checkpoints. Abstract behind an interface so we can swap later.

Keeping It Light

Concern: Would full server mode be too heavy for a local client?

Solution: Single package, separate directory, optional dependencies. The hub code only loads when you run leonai serve.

leonai/ |-- agent.py |-- middleware/ |-- tui/ # CLI/TUI (current) | |-- hub/ # NEW - optional, lazy-loaded |-- server.py # FastAPI app |-- coordinator.py # Multi-agent |-- federation.py # Peer connections |-- web/ # Static frontend

Usage

leonai

# Start hub server with web UI
leonai serve

# Connect to peers on the network
leonai serve --port 8000 --peers http://192.168.1.5:8000

Open Questions

Server discovery: Manual config or auto-discovery (mDNS)?

Manual is simpler and more predictable. mDNS is convenient but can be flaky. Probably start with manual, add mDNS later as opt-in.

Authentication: Shared secret, certificates, or open (LAN only)?

For LAN use, open is fine. For internet, need at least shared secret. Certificates are more secure but harder to set up.

Conflict resolution: Two agents edit same file - who wins?

Last-write-wins is simple but can lose work. Could use file locking, but that adds complexity. Maybe just fail loudly and let humans resolve.

Next Steps

  1. Implement SQLite message queue with abstract interface
  2. Build minimal FastAPI server with WebSocket support
  3. Create coordinator for local multi-agent orchestration
  4. Add federation layer for peer-to-peer connections
  5. Build web UI (probably React or vanilla JS)

The goal is to keep LEON's core simple while enabling powerful multi-agent workflows for those who need them. Complexity should be opt-in, not mandatory.
