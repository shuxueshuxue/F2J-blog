FUSE Explained: How AI Sandboxes Get Persistent Filesystems

February 8, 2026 — A companion to Sandbox Workspace Persistence: A Comparative Analysis

AI agents write files the way any program does: open(), write(), close(). They don't call storage APIs. They don't know they're inside an ephemeral sandbox. So when you need their workspace to survive a sandbox restart, you have two options: copy files in and out at lifecycle boundaries, or make remote storage look like a local filesystem.

FUSE is how you do the second one.

What is FUSE?

FUSE (Filesystem in Userspace) is a Linux kernel module that lets you implement a filesystem as a regular program instead of a kernel driver. It has three parts:

  1. The FUSE kernel module (fuse.ko) -- loaded into the kernel, registers itself with the VFS (Virtual Filesystem Switch). The VFS is the abstraction layer that routes all filesystem calls (open, read, write, stat, etc.) to the right filesystem driver -- ext4, NFS, or in our case, FUSE.
  2. The libfuse library -- a userspace library that handles the protocol between the kernel module and your daemon.
  3. Your userspace daemon -- the actual program that decides what happens when someone reads or writes a file. For gcsfuse, this daemon translates filesystem operations into GCS API calls.

Here's the request flow when an agent writes a file to a FUSE-mounted directory:

Agent: open("/workspace/result.py", "w") | v Kernel VFS: "this path is on a FUSE mount" | v FUSE kernel module: serialize request, write to /dev/fuse | v Userspace daemon (gcsfuse): read from /dev/fuse | - translate to GCS API call | - PUT object to gs://bucket/thread-id/result.py | - write response back to /dev/fuse v FUSE kernel module: deserialize response | v Kernel VFS: return success to agent | v Agent: file written (doesn't know it went to GCS)

The key insight: every file operation crosses the kernel-userspace boundary twice. Once going down (app to kernel to daemon), once coming back up (daemon to kernel to app). This is the fundamental cost of FUSE -- and the reason it exists. Writing a kernel filesystem driver is hard, dangerous, and requires kernel rebuilds. FUSE lets you write one in Python if you want.

Why FUSE for Sandboxes?

The alternative is what we call "tar sync" -- archive the workspace on save, re-extract on restore. It works. We benchmarked it at 1.06s save / 2.44s restore for a small workspace. But it has a structural problem: if the sandbox crashes between saves, you lose everything since the last checkpoint.

With FUSE, every write goes to durable storage immediately. There is no save step. When the sandbox dies, the files are already in GCS. When a new sandbox starts, you mount the same bucket prefix and the files are there.

The reason you can't just use the GCS SDK directly is that agents don't know about GCS. An agent runs python script.py, which calls open("output.csv", "w"). That's a syscall. It hits the kernel. FUSE intercepts it and routes it to cloud storage. The agent, the script, and Python itself are all unaware.

gcsfuse in Practice

In LEON's GCSFuseStorage, the restore() method mounts a GCS bucket inside the sandbox. Here's the actual mount command from our implementation:

sudo gcsfuse --key-file /home/user/.gcs-key.json \
    --implicit-dirs \
    --only-dir {thread_id} \
    -o allow_other \
    --file-mode=0666 --dir-mode=0777 \
    leon-sandbox-workspaces /home/user/workspace

Each flag solves a specific problem:

  • --implicit-dirs -- GCS is a flat key-value store, not a real filesystem. There are no directories, just keys with / in them. This flag makes gcsfuse synthesize directory entries from object key prefixes, so ls and os.listdir() work as expected.
  • --only-dir {thread_id} -- Per-thread isolation. Each agent conversation gets its own prefix in the bucket. Thread abc123 sees only objects under gs://leon-sandbox-workspaces/abc123/. One bucket, many workspaces.
  • --file-mode=0666 --dir-mode=0777 -- gcsfuse runs as root (needs sudo for the mount syscall), but the sandbox agent runs as user. Without these flags, the mounted files are owned by root and the agent can't write to them.
  • -o allow_other -- Same ownership problem, different angle. By default, only the user who mounted the filesystem can access it. This flag lets other users (the sandbox's user account) read and write.

And the save() method? It's literally a no-op:

def save(self, provider, session_id, thread_id):
    """No-op -- FUSE writes go directly to GCS."""
    pass

Daytona's Approach: Platform-Managed FUSE

Daytona uses the same underlying technology -- FUSE backed by S3 -- but manages it at the platform level. You don't install gcsfuse, inject credentials, or run mount commands. You declare a volume:

params = CreateSandboxFromSnapshotParams(
    volumes=[VolumeMount(volume_id=volume.id, mount_path="/workspace")]
)

Daytona handles the daemon lifecycle, the S3 credentials, and the mount. From LEON's perspective, there is no WorkspaceStorage implementation needed at all -- the volume persists independently of the sandbox.

The tradeoff is control. When Daytona's FUSE layer has bugs -- and it does (mv and touch are broken as of February 2026, see #3331) -- you can't fix them. With gcsfuse, you pick the version, set the flags, and debug the daemon yourself.

The Tradeoffs

FUSE is not free. Every file operation pays a tax:

Latency: Each syscall crosses the kernel-userspace boundary twice, then makes a network round-trip to the storage backend. A local stat() takes microseconds. A FUSE stat() over GCS takes milliseconds.

Metadata is expensive: Operations like ls -la on a directory with 100 files means 100+ stat() calls, each hitting GCS. Tools like find or git status that walk directory trees will be noticeably slower.

Not for databases: SQLite, Postgres, or anything that does random seeks and fsync will perform badly. FUSE filesystems are not POSIX-complete -- some operations (hard links, extended attributes) may not be supported.

But for AI agent workspaces -- Python scripts, Jupyter notebooks, CSV outputs, small data files -- the latency is acceptable. Our benchmarks show 3.83s cold restore with a pre-built template (vs 12.93s with runtime gcsfuse installation). After that, individual file operations add single-digit milliseconds of overhead.

In Our Architecture

LEON's sandbox system has a WorkspaceStorage interface with three implementations. Two of them (SQLite, tar sync) copy files at lifecycle boundaries. The third (gcsfuse) mounts storage directly:

WorkspaceStorage | |-- SQLiteStorage save: download each file -> SQLite BLOB | restore: upload each file from SQLite | |-- GCSTarSyncStorage save: tar -> base64 -> GCS upload | restore: GCS download -> untar | +-- GCSFuseStorage save: pass restore: mount gcsfuse -> done

The FUSE approach inverts the persistence model. Instead of "save state before shutdown," it's "state is always saved." The restore() method doesn't transfer data -- it sets up a mount point so the data is accessible. The save() method does nothing because there's nothing to do.

When to use FUSE: Long-running agent sessions where crash resilience matters and you can tolerate slightly slower file I/O. Use the tar sync approach when you want simpler infrastructure and faster cold starts.

The custom template matters: Our E2B template (leon-gcsfuse:v1.0) pre-installs gcsfuse in the sandbox image. Without it, every cold start pays a ~12s installation penalty. With it, cold restore drops to ~4s -- competitive with tar sync's 2.4s restore.
