Sandbox Workspace Persistence: A Comparative Analysis

February 8, 2026

When building AI agent runtimes that execute code in cloud sandboxes, one fundamental problem emerges: how do you persist workspace files across sandbox lifecycle events?

Sandboxes are ephemeral by design. They spin up, run code, and die. But AI agents need continuity -- the files from yesterday's conversation should be there when the user comes back today. This post documents our investigation into four different persistence strategies for the LEON agent runtime.

The Problem

LEON supports multiple sandbox providers: E2B (microVMs), Daytona (Docker containers), AgentBay (Alibaba Cloud), and local Docker. Each has different persistence characteristics:

Provider Native Volumes Survives Stop/Start Survives Destroy
E2BNoneFull VM state (pause/resume)Nothing
DaytonaYes (FUSE/S3)Disk stateNothing (unless volumes)
AgentBayYes (OSS context)Built-inBuilt-in
DockerYes (bind mounts)Built-inBuilt-in

E2B is the problem child. It has no native persistent storage. The previous workaround was downloading every file from the workspace into SQLite BLOBs on destroy, then re-uploading on recreate. This works for tiny workspaces but doesn't scale.

Four Approaches Tested

1. E2B + SQLite (Baseline)

The original approach. On destroy, walk the workspace directory tree, download each file via the E2B SDK, store as BLOBs in a local SQLite database. On recreate, upload them all back.

Pros: No external dependencies. Works offline.
Cons: O(n) API calls per file. Practical limit ~50MB. Binary files are painful.

2. E2B + GCS Tar Sync

Tar the entire workspace inside the sandbox, base64-encode it (because the E2B file API is text-only), download to the host, upload to Google Cloud Storage. Reverse on restore.

Save: sandbox$ tar czf -> base64 -> host reads text -> decode -> GCS upload Restore: GCS download -> host -> sandbox$ base64 -d -> tar xzf

Pros: Single archive instead of per-file transfers. Scales to hundreds of MB. Cloud-backed durability.
Cons: Full workspace re-upload on every save. Base64 overhead (33% size increase in transit).

3. E2B + GCSFuse

Mount a Google Cloud Storage bucket directly inside the sandbox via gcsfuse. Writes go straight to GCS in real-time. Per-thread isolation via --only-dir.

Restore: inject credentials -> install gcsfuse (if needed) -> mount bucket Save: no-op (already in GCS)

Pros: Zero save time. Real-time persistence. No data loss on crash.
Cons: ~13s cold start (gcsfuse install). Metadata operations have FUSE latency. Requires sudo in sandbox.

4. Daytona + Native Volumes

Daytona has first-class FUSE volumes backed by S3. Create a named volume, attach it at sandbox creation time. The volume persists independently of the sandbox lifecycle.

volume = daytona.volume.get("leon-{thread_id}", create=True)
params = CreateSandboxFromSnapshotParams(
    volumes=[VolumeMount(volume_id=volume.id, mount_path="/workspace")]
)

Pros: Zero application-level code. Volumes survive sandbox deletion. Shared across sandboxes.
Cons: Known bugs (broken mv/touch -- #3331). Volume creation race condition (#2770).

Key Observations

GCSTarSync is the sweet spot for E2B. It's 2.6x faster than SQLite on save, 1.6x faster on restore, and scales to large workspaces. The base64 encoding overhead is negligible for typical AI agent workspaces.

GCSFuse has zero save cost but pays on restore. The cold start penalty is brutal without a custom template. Once mounted, writes are transparent -- no sync logic needed. Best for long-running sessions where the agent writes frequently.

Daytona volumes just work -- no application code needed. The volume API has rough edges (race conditions, FUSE bugs) but the architecture is right. Zero overhead at the LEON layer.

SQLite should be deprecated for anything beyond toy workspaces. It's the slowest approach and doesn't scale.

Architecture

The implementation introduces a WorkspaceStorage interface that plugs into the sandbox lifecycle:

RemoteSandbox |-- on_session_ready -> run init commands -> storage.restore() |-- on_before_pause -> storage.save() |-- on_before_destroy -> storage.save() | |-- WorkspaceStorage (ABC) | |-- SQLiteStorage -- files in SQLite BLOBs | |-- GCSTarSyncStorage -- tar -> GCS bucket | +-- GCSFuseStorage -- gcsfuse mount | +-- DaytonaProvider +-- Native volumes (no WorkspaceStorage needed)

Configuration is in ~/.leon/sandboxes/e2b.json:

{
  "provider": "e2b",
  "e2b": {
    "storage": "gcs_sync"
  },
  "gcs": {
    "key_file": "~/.leon/gcs-key.json",
    "bucket": "leon-sandbox-workspaces"
  }
}

Verdict

For E2B: Use gcs_sync (tar sync) as the default. Best balance of speed, reliability, and simplicity. Use gcs_fuse only if you need real-time persistence and can tolerate the cold start.

For Daytona: Use native volumes. No contest.

For production: The real answer is that E2B should add native volumes (there's a snapshot PR in progress). Until then, GCS tar sync bridges the gap.
