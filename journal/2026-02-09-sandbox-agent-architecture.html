1. Architecture Essence

The system is organized by durability boundary and ownership boundary.

1.1 Durability

  • Durable:
  • Agent
  • Thread
  • AbstractTerminal state (cwd, env_delta)
  • ChatSession records
  • SandboxLease identity
  • StorageBinding
  • Collaboration channel/member/message
  • Ephemeral:
  • Physical terminal runtime process
  • Sandbox instance (provider VM/container/sandbox process)

1.2 Ownership

  • Agent owns default policy (sandbox type, default workspace key, memory root)
  • Thread owns task timeline and terminal identity
  • ChatSession owns runtime lifecycle window
  • Lease owns compute handle and provider instance convergence

Core theorem:
Policy envelope (ChatSession) must contain runtime lifecycle; durable identity must outlive compute.

2. Canonical Data Model

2.1 Runtime Core

  • abstract_terminals
  • terminal identity per thread
  • persisted state snapshot (cwd, env_delta_json, state_version)
  • chat_sessions
  • lifecycle/policy window
  • status: active|idle|paused|closed
  • idle TTL and max duration policy
  • sandbox_leases
  • durable compute handle
  • workspace_key continuity anchor
  • pointer to current instance
  • sandbox_instances
  • ephemeral provider instance records and status

2.2 Product Layer

  • workspace_storages
  • owner-scoped binding to context/mount/bucket/workspace_key
  • agents
  • durable agent identity and defaults
  • agent_threads
  • mapping agent -> many task threads
  • collab_channels
  • collab_channel_members
  • collab_channel_messages

3. Runtime Execution Path

3.1 Orchestration Graph

Thread
  -> ChatSession (policy)
      -> PhysicalTerminalRuntime (ephemeral)
          -> AbstractTerminal (state snapshot)
          -> SandboxLease (compute handle)
              -> SandboxInstance (provider resource)

3.2 Command Execution

  1. Resolve thread -> session via SandboxManager.get_sandbox(thread_id)
  2. Runtime executes command
  3. Runtime updates terminal snapshot (cwd, env_delta)
  4. Lease converges provider instance status when needed

3.3 Provider Strategies

  • Local: persistent shell process per session window
  • Remote: wrapped command execution + state hydration/persist markers

4. Lifecycle State Semantics

4.1 ChatSession state machine

  • active -> paused via pause
  • paused -> active via resume
  • active|idle|paused -> closed via destroy/expire
  • active -> idle via policy timer (internal)

Invariant:
- Physical runtime cannot outlive ChatSession

4.2 Lease/Instance state semantics

  • Lease may have 0..1 current instance
  • Instance states provider-normalized to running|paused|detached|unknown
  • Lease can recreate instance when prior one is dead/detached

5. Storage Model (Context / Mount / Bucket)

Storage continuity is represented by workspace_storages and consumed by lease creation.

5.1 Ownership and precedence

Current effective precedence:
1. explicit thread binding
2. inherited from agent default workspace key at thread creation

5.2 Provider mapping

  • AgentBay: context-based continuity (context_id + mount path)
  • Docker: volume + mount path continuity
  • Daytona: workspace key / persisted disk continuity
  • E2B: no native durable context, optional snapshot strategy in metadata
  • Object store: bucket URI recorded as binding metadata

Practical rule:
workspace_key is continuity anchor; instances are replaceable executors.

6. Agent Model

6.1 Why agent exists

Without agent entity, thread-scoped policy duplicates across tasks and loses persona-level continuity.

6.2 Current behavior

  • create agent with default sandbox + optional workspace key
  • create multiple threads under one agent
  • thread inherits policy defaults from agent
  • each thread still has isolated terminal state and lifecycle

This matches product intent:

agentA
  - thread1 (task)
  - thread2 (task)

7. Cross-Agent Collaboration Contract

Collaboration is explicit, not implicit runtime side-effect.

Contract entities:
- channel (workspace anchored)
- member (agent membership + role)
- message (agent-authored content + metadata)

Benefits:
- multiple agents can coordinate over same workspace domain
- terminal/runtime isolation remains per thread
- future orchestration can add automation on top of durable message contract

8. Ground Truth Resource Visibility (Leak Control)

8.1 Problem solved

Thread/chat-session-centric inspect can hide real running resources.

8.2 Current design

Inspect now uses lease/provider-first ground truth:
- show tracked lease-backed sessions
- show untracked resources ((untracked))
- show provider orphans ((orphan) equivalent source)

Session list includes provenance fields:
- source
- lease_id
- instance_id
- chat_session_id

8.3 Mutability

Session-level mutation API exists for all rows (tracked or untracked):
- POST /api/sandbox/sessions/{session_id}/pause
- POST /api/sandbox/sessions/{session_id}/resume
- DELETE /api/sandbox/sessions/{session_id}

Internal routing:
- manager-thread path (tracked thread)
- manager-lease path (untracked lease row)
- provider-direct path (orphan provider row)

This closes the gap: visible resource => actionable control.

13. Experimental Thinkings (Separate Section)

This section records explicit exploration and tradeoffs (not final dogma).

13.1 Experiment A: Thread-centric storage binding only

Hypothesis:
- thread-level storage binding is sufficient

Result:
- works technically
- duplicates policy for same agent persona across many tasks

Conclusion:
- insufficient as long-term product model

13.2 Experiment B: Agent-centric ownership + task threads

Hypothesis:
- agent should own defaults, thread should own task execution

Result:
- better ownership separation
- natural support for "same agent, multiple tasks"

Conclusion:
- accepted into final design

13.3 Experiment C: Cross-agent collaboration as explicit contract

Hypothesis:
- collaboration should be modeled explicitly (channel/member/message), not by shared runtime accident

Result:
- deterministic and auditable collaboration layer
- compatible with shared workspace + isolated terminals

Conclusion:
- accepted into final design

13.4 Ground-truth inspect experiment

Hypothesis:
- inspect should be lease/provider-first, not chat-session-first

Result:
- exposed hidden running resources
- revealed actionability gap for untracked rows
- session-level mutation API closed the loop

Conclusion:
- accepted; critical for cost safety and leak prevention

13.5 Rejected / deferred ideas

  • "Only thread-level controls" as sole control plane: rejected
  • Implicit cross-agent communication via shared filesystem only: rejected
  • Making sandbox instance the durable source-of-truth: rejected

Deferred:
- strict state-machine transition gateway
- move to Postgres/Supabase
- full event/audit stream for lifecycle transitions

14. One-line Summary

The architecture now treats compute as replaceable, identity/policy as durable, collaboration as explicit contract, and resource visibility/control as ground-truth first.
